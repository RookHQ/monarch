# Adding a component to Monarch for iOS

This is the recipe for covering one entry of `platforms/parity.json` on iOS.
Many people do this at the same time, each in a private copy of
`platforms/ios`, and only their new files are copied back. So the first rule
is:

**Adding a component only adds files. You never edit a file that already
exists.**

Every list that would otherwise be shared (the inventory, the compiled
examples, the test fixture registry, the sample's navigation, the strings) is
either one file per component or generated by `Scripts/generate.py`.

## 1. Read the plan entry

Find the entry in `platforms/parity.json` by its `id`. You need:

| Field          | Use                                                                       |
| -------------- | ------------------------------------------------------------------------- |
| `id`           | The inventory file name, `inventory/<id>.json`, and the fixtures id.      |
| `family`       | The folder (see the table below).                                         |
| `title`        | The inventory `title`.                                                    |
| `ios.coverage` | What you deliver: `build`, `style`, `native`, `compose` or `web-only`.    |
| `ios.name`     | The Swift type name. Use it exactly; Android uses the same name.          |
| `ios.uses`     | The SwiftUI API to build on.                                              |
| `dependsOn`    | Entries that must exist first. Use those components; do not rebuild them. |

Family folders are the web family in PascalCase:

| `family`      | Folder          | `family`     | Folder         |
| ------------- | --------------- | ------------ | -------------- |
| actions       | `Actions`       | intelligence | `Intelligence` |
| billing       | `Billing`       | interaction  | `Interaction`  |
| charts        | `Charts`        | layout       | `Layout`       |
| collaboration | `Collaboration` | navigation   | `Navigation`   |
| crm           | `Workflow`      | overlays     | `Overlays`     |
| data-display  | `DataDisplay`   | scheduling   | `Scheduling`   |
| data-grid     | `DataGrid`      | search       | `Search`       |
| feedback      | `Feedback`      | technical    | `Technical`    |
| files         | `Files`         | typography   | `Typography`   |
| forms         | `Forms`         | workflow     | `Workflow`     |
| geo           | `Geo`           | identity     | `Identity`     |

## 2. The files you create

Below, `<Name>` is `ios.name` (for example `MonarchBadge`), `<Family>` is the
folder from the table and `<id>` is the web id.

### Coverage `build`, or `style` with a new Swift type

| #   | File                                                                                                                         | Required                                                                 |
| --- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1   | `Sources/MonarchUI/Components/<Family>/<Name>/<Name>.swift`                                                                  | Yes. The public type, with a `#Preview`.                                 |
| 2   | `Sources/MonarchUI/Components/<Family>/<Name>/<Name><Option>.swift`                                                          | One file per further public type (a variant or size enum).               |
| 3   | `Sources/MonarchUI/Components/<Family>/<Name>/<Name>Tokens.swift`                                                            | Yes if the component has any size, spacing or colour decision. Internal. |
| 4   | `Sources/MonarchUI/Components/<Family>/<Name>/<Name>Strings.swift` and `Sources/MonarchUI/Resources/en.lproj/<Name>.strings` | Only if the component has built-in text.                                 |
| 5   | `Tests/MonarchUITests/Components/<Family>/<Name>Tests.swift`                                                                 | Yes. Fixtures and logic tests.                                           |
| 6   | `Sample/Sources/Sections/<Family>/<Name>Section.swift`                                                                       | Yes. The catalogue page.                                                 |
| 7   | `inventory/<id>.json`                                                                                                        | Yes. Documentation and compiled examples.                                |

### Coverage `style` that reuses an existing type

For example `menu-button`, which is `Menu` with the existing
`MonarchButtonStyle`. No source files.

| #   | File                                                             | Required                                                                                       |
| --- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 1   | `inventory/<id>.json`                                            | Yes. `name` is the existing type.                                                              |
| 2   | `Tests/MonarchUITests/Components/<Family>/<PascalId>Tests.swift` | Yes. Fixtures (`enum <PascalId>Fixtures`) that show the native control with the Monarch style. |
| 3   | `Sample/Sources/Sections/<Family>/<PascalId>Section.swift`       | Yes.                                                                                           |

`<PascalId>` is the id in PascalCase: `menu-button` gives `MenuButton`.

### Documentation-only entries: `native`, `compose`, `web-only`

Monarch ships no Swift type. The entry is the documentation.

| #   | File                                                       | Required                                                                                                     |
| --- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 1   | `inventory/<id>.json`                                      | Yes.                                                                                                         |
| 2   | `Sample/Sources/Sections/<Family>/<PascalId>Section.swift` | For `native` and `compose`: yes, so the catalogue shows the native control in the theme. For `web-only`: no. |

Rules for these entries (the generator enforces the ones marked ✔):

- `name` is `null` ✔.
- `native`: `kind` is `native`, `category` is `A` ✔. `wrapsNative` names the
  exact SwiftUI API, including the style or modifier that makes it the answer,
  for example `Picker with .pickerStyle(.inline)` ✔ (non-empty). At least one
  compiled example that uses that API inside the Monarch theme ✔.
  See `inventory/switch.json` and `inventory/radio-group.json`.
- `compose`: `kind` is `recipe` ✔. `wrapsNative` names the SwiftUI containers
  used, `dependsOn` lists the Monarch components the recipe is made of, and
  at least one example is the complete recipe ✔ (compiled and rendered).
  `category` is `B`.
- `web-only`: `kind` is `none` ✔, `wrapsNative` is `null`, `examples` may be
  empty, `category` is `A`. `summary` says what the web component is,
  `platformNotes` says why it has no meaning in a native app, and
  `whenToUse` says what an iOS app does instead.

## 3. What you must not touch

- `Package.swift`, `.swift-format`, `Scripts/`, `README.md`, `CHANGELOG.md`,
  `docs/`, `inventory/schema.json`.
- Anything generated: `components.json`, every `Generated/` folder,
  `Sample/MonarchCatalogue.xcodeproj`. They change in your copy when you run
  the scripts; that is expected. Do not copy them back.
- `api/`. The API baseline is regenerated once, at merge. Do not run
  `Scripts/api.sh --update`.
- `Sources/MonarchTokens/`. Generated from `packages/tokens`.
- `Sources/MonarchUI/Theme`, `Foundations`, `Accessibility`, `Internal`, and
  every other component's folder, tests, page and inventory file. If you need
  a shared helper that does not exist, keep it `private` in your own folder
  and say so when you hand over; it is promoted to `Internal/` at merge.
- `Documentation.docc/MonarchUI.md`. New public types appear in the
  documentation without being listed there.

What you hand over is exactly the new files from section 2, and nothing
else. `.build`, `.swiftpm` and the generated files stay behind.

## 4. API conventions

### Style first

1. If SwiftUI has the control, **ship a style** (`ButtonStyle`, `ToggleStyle`,
   `ProgressViewStyle`, `LabelStyle`, `GroupBoxStyle`, …) with a static
   accessor: `extension ToggleStyle where Self == MonarchCheckboxToggleStyle {
static var monarchCheckbox … }`. The control stays the standard control.
2. Add a `Monarch<Name>` **view** only when a wrapper adds value the style
   cannot: a label with helper and error text, a loading state, a fixed
   composition. The view uses the standard control inside.
3. Build a **custom view** only when SwiftUI has no equivalent.
4. Do not recreate a SwiftUI control. No UIKit unless SwiftUI cannot do it;
   if you use it, say why in a comment at the import.

A style or view that needs the environment reads it in a private inner
`View`, because style values cannot (see `MonarchButtonStyle.swift`).

### Names and vocabulary

- The type is `ios.name`. Option enums are `<Name>Variant`, `<Name>Size`;
  style accessors are `.monarch…`.
- Use the shared words and nothing else:
  - variants of actions: `primary`, `secondary`, `ghost`, `danger`
  - emphasis: `subtle`, `solid`, `outline`
  - sizes: `sm`, `md`, `lg` (no `xs` on touch)
  - tones: the existing `MonarchTone` (`neutral`, `info`, `success`,
    `warning`, `danger`). Do not declare another tone enum.
- Boolean parameters read as assertions: `isLoading`, `isSecure`. Bindings
  come from SwiftUI convention: `text:`, `isOn:`, `selection:`.

### Parameter order

`init(_ title or label, <binding>, <content strings>, systemImage:, tone:,
variant:, size:, <state flags>, <string overrides>, <layout flags>,
action or @ViewBuilder content last)`.

Every parameter except the title, the binding and the action has a default.
Compare `MonarchButton.init` and `MonarchBadge.init`.

### Strings

- Text the app supplies (titles, messages, labels) is a plain `String` that
  the app has already localised.
- Text Monarch supplies (spoken accessibility text, a default button title)
  lives in **your own table**, `Resources/en.lproj/<Name>.strings`, with keys
  `monarch.<nameInLowerCamelCase>.<key>` and a comment above each key. Read it
  through a small enum in your folder:

  ```swift
  enum MonarchButtonStrings {
      static var loading: String { MonarchStrings.string("monarch.button.loading", table: "MonarchButton") }
  }
  ```

- Every built-in string can be replaced by a parameter (`loadingLabel:`,
  `toneLabel:`), `nil` by default.
- There is no shared `Localizable.strings`; the generator rejects one.

### Colours, sizes and shape

- Colours come from the theme by role: `@Environment(\.monarchTheme)`, then
  `theme.colors.textDefault` or `theme.colors[role: role]`. Never
  `MonarchTokens.light…`, never `Color.red`, `.white`, `.black`, `.gray`,
  `Color(red:…)`, hex values or opacity literals. Use the role that exists
  for the state (`textDisabled`, `bgMuted`) instead of dimming.
- Decide colours in a **pure function** in `<Name>Tokens.swift` that returns
  role key paths (`MonarchColorRole`) for a state, and test it.
- `MonarchColorRole` is a `KeyPath`, which is not `Sendable`, so a stored
  `static let` of one does not compile in Swift 6 language mode. Write a
  fixed role as a computed property:
  `static var border: MonarchColorRole { \.borderDefault }`.
- Sizes, spacing, radii and durations come from `MonarchTokens.Space`,
  `.Control`, `.Radius`, `.FontSize`, `.Duration` through static constants
  in `<Name>Tokens.swift`. No number in a view body except 0 and 1 and
  ratios named in the tokens file.
- Text uses `.monarchTextStyle(_:)`. Never `.font(.system(size:))` on text.
  Scale other lengths with `@ScaledMetric` (see `MonarchIcon`).

### Layout, text size and motion

- Leading and trailing only; never left and right. Directional symbols use
  the `.forward`/`.backward` names. SwiftUI mirrors a `Shape`'s path in
  right-to-left layouts; `Canvas` drawing and `offset(x:)` are not mirrored
  for you. Check both directions.
- Nothing has a fixed height that contains text. Use `minHeight`, let text
  wrap, and check the fixture at the largest size.
- Every interactive element has a touch target of at least 44 by 44 points:
  `.monarchMinimumHitTarget()` on the label, inside the control.
- Animate with `.monarchAnimation(_:easing:value:)`, or
  `theme.motion.animation(…, reduceMotion:)` with
  `@Environment(\.accessibilityReduceMotion)`. A repeating animation must
  have a still form for Reduce Motion (see `MonarchProgressViewStyle`).

### Accessibility

- Keep the standard control and you keep its role, value and gestures.
- A custom look on a control gives VoiceOver the real control with
  `.accessibilityRepresentation` (see `MonarchCheckboxToggleStyle`).
- Decorative images are hidden: `MonarchIcon(systemName:)` does this.
  Meaningful ones take a label: `MonarchIcon(systemName:label:)`.
- Group what is read together with `.accessibilityElement(children: .combine)`
  and keep actions as separate elements (see `MonarchBanner`).
- Never rely on colour alone: a tone is also an icon and a spoken name
  (`MonarchToneStrings.name`), an error is also an icon and text, a selected
  state is also a glyph.
- State is a value or a trait (`accessibilityValue`, `.isSelected`,
  `.isHeader`, `.updatesFrequently`), not part of the label.
- Announce what appears without focus moving:
  `AccessibilityNotification.Announcement(…).post()`.

### Images

A component that shows a picture (avatar, favicon, link card) follows one
convention, implemented by `Internal/MonarchRemoteImage.swift`:

- Two initialisers and no more: one takes `image: Image?`, one takes
  `url: URL?`. All other parameters are the same in both.
- A URL is loaded with SwiftUI's `AsyncImage` (the shared `URLSession`).
  Monarch adds no networking, caching or image dependency. An app with its
  own image pipeline loads the image and passes the `Image`.
- The placeholder (initials, a symbol, a letter tile) is shown while
  loading, on failure and when there is no source. Failure is not an error
  state.
- The component clips the image and decides what VoiceOver reads.

```swift
MonarchRemoteImage(url: url) { Text(initials) }
    .frame(width: size, height: size)
    .clipShape(Circle())
```

### Experimental API

Mark every top-level public declaration of a component that is not ready to be
stable with `@_spi(Experimental) public`, and set `"status": "experimental"` in
the inventory. An experimental declaration never appears in a stable signature:
`Scripts/api.sh` fails when one does.

- `Scripts/generate.py` checks that an experimental component marks every
  public declaration, and that an available one marks none.
- A file that uses an experimental declaration writes
  `@_spi(Experimental) import MonarchUI`, a test with
  `@_spi(Experimental) @testable import MonarchUI`. The examples of an
  experimental entry are compiled that way for you. An example of a stable
  entry that shows an experimental symbol sets `"experimental": true`.
- Status and `layer` are the same as on Android. `scripts/native/status-check.mjs`
  (`npm run native:status:check`) compares the two inventories and
  `platforms/parity.json`.

All in `Sources/MonarchUI/`; each has a documentation comment.

| A colour role in a variable            | `MonarchColorRole`, `theme.colors[role:]` (`Theme/MonarchColors.swift`)                                                                            |
| Tone colours and icon                  | `MonarchTonePalette.palette(for:)` gives `subtle`, `strong`, `solid`, `onSolid`, `border`, `symbol` (`Internal/MonarchTonePalette.swift`)          |

| Type                                   | `.monarchTextStyle(_:)`; internally also `.monarchTextStyle(_:weight:)`                                                                            |
| Icons                                  | `MonarchIcon` (`Foundations/Icon/`)                                                                                                                |
| Remote or local image                  | `MonarchRemoteImage` (`Internal/MonarchRemoteImage.swift`)                                                                                         |
| Previews                               | `MonarchPreviewMatrix { … }` (`Internal/MonarchPreviewMatrix.swift`)                                                                               |

## 6. Previews

End the main file with one preview that shows every variant and state. The
matrix shows it in the light theme, the dark theme and at the largest text
size.

```swift
#if DEBUG
    #Preview("MonarchBadge") {
        MonarchPreviewMatrix {
            // every variant and state
        }
    }
#endif
```

## 7. Tests

One file, `Tests/MonarchUITests/Components/<Family>/<Name>Tests.swift`, with
two things in it.

**Fixtures.** An enum named `<Name>Fixtures` that conforms to
`ComponentFixtures`. `id` is the inventory id. Do not register it anywhere:
`Scripts/generate.py` finds every `enum …: ComponentFixtures` under
`Tests/MonarchUITests` and writes `Generated/FixtureRegistry.generated.swift`.
`ComponentMatrixTests` then hosts each fixture in all four themes, at the
default and the largest Dynamic Type size, left to right and right to left,
and fails on a crash, an empty layout or a failed draw.

Fixtures must cover every variant, size, tone and state (disabled, loading,
error, empty, long text). Several small fixtures are better than one large
one, because the test output names the fixture.

**A suite** named `<Name>Tests` (the fast loop finds it by that name) with:

- the colour and state logic: every pure function in `<Name>Tokens.swift`,
  for every variant and for pressed and disabled;
- the accessibility logic: labels, values and hints are built by pure
  functions and tested as strings (see `MonarchTextFieldTests`). SwiftUI
  gives unit tests no access to the accessibility tree, so anything VoiceOver
  reads that can be computed must be computed outside the view body;
- the built-in strings resolve (not equal to their keys);
- size checks that need real Dynamic Type or touch targets, inside
  `#if os(iOS)` with `Host.layout(_:)` (they run on the simulator at merge).

Use Swift Testing (`import Testing`, `@Test`, `#expect`). Use
`@testable import MonarchUI` to reach internal tokens.

**Compiled examples.** Every `examples[].code` in your inventory file is
compiled into `Generated/Examples/<Family>Examples.generated.swift` and
rendered by `InventoryExampleTests`. You write no test for this.

## 8. The sample page

`Sample/Sources/Sections/<Family>/<Name>Section.swift`:

```swift
import MonarchUI
import SwiftUI

struct MonarchBadgeSection: CataloguePage {
    static let title = "Badge"

    var body: some View {
        // Views in a leading-aligned column. No ScrollView, no navigation
        // title: the catalogue adds them.
    }
}
```

The file name is the type name. The family in the navigation is the folder
name. `Scripts/generate.py` writes `CatalogueRegistry`; do not edit
`CatalogueView`. Use `CatalogueCaption("…")` for a heading inside the page.
The page should be interactive where the component is.

## 9. The inventory file

`inventory/<id>.json` is the component's documentation. `components.json` is
generated from all of them. The file is validated against
`inventory/schema.json`; unknown fields are rejected.

| Field                       | Content                                                                                                                          |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `id`                        | The web id. Equal to the file name.                                                                                              |
| `name`                      | The Swift declaration (`ios.name`), or `null` when nothing is shipped.                                                           |
| `title`                     | `title` from parity.json.                                                                                                        |
| `family`                    | `family` from parity.json, unchanged (`data-display`, not `DataDisplay`).                                                        |
| `category`                  | `A` native adoption, `B` style or wrapper over a system control, `C` custom.                                                     |
| `coverage`                  | `ios.coverage` from parity.json. If you find the plan is wrong, write what you built and say so when you hand over.              |
| `kind`                      | `style`, `wrapper`, `custom`, `modifier`, `native`, `recipe` or `none`.                                                          |
| `wrapsNative`               | The exact SwiftUI API underneath. `null` only for `web-only`.                                                                    |
| `status`                    | `available`, `experimental`, `planned` or `deprecated`.                                                                          |
| `layer`                     | `components`, or `patterns` for an experimental domain composite (ADR 0017). The same value as on Android.                       |
| `since`                     | The version that adds it. Entries from before the unified version say `0.1.0`.                                                   |
| `summary`                   | One sentence: what it is.                                                                                                        |
| `whenToUse`, `whenNotToUse` | One or two sentences each. Name the alternative.                                                                                 |
| `api`                       | The public signatures, copied from the source.                                                                                   |
| `options`                   | One object per parameter: `name`, `type`, `default` (`"required"` if none), `description`. Empty for a style with no parameters. |
| `states`                    | One object per state: `name`, `description` of what changes.                                                                     |
| `appearance`                | How it looks in light, dark and high contrast. One or two sentences, naming the colour roles in words.                           |
| `platformNotes`             | How it differs from Android and the web, and why. Say what the web has that this does not offer.                                 |
| `accessibility`             | Concrete behaviours, one per string. Only what the code does.                                                                    |
| `edgeCases`                 | Long text, empty values, extremes, things that surprise.                                                                         |
| `tests`                     | The suites that cover it: `<Name>Tests`, `ComponentMatrixTests`, `InventoryExampleTests`.                                        |
| `examples`                  | Objects with `title` and `code`; optional `setup` and `imports`. See below.                                                      |
| `webEquivalent`             | The React component name, or `null`.                                                                                             |
| `dependsOn`                 | Inventory ids it builds on.                                                                                                      |

**Examples.** `code` is the body of a SwiftUI view. If it needs state, the
environment or a function, declare them in `setup`; both are shown in the
documentation and placed in the same view when compiled:

```json
{
  "title": "A checkbox",
  "setup": "@State private var isOn = true",
  "code": "Toggle(\"Email me a receipt\", isOn: $isOn)\n    .toggleStyle(.monarchCheckbox)"
}
```

`imports` lists system frameworks beyond SwiftUI, MonarchUI and
MonarchTokens (for example `["MapKit"]`). Examples are rendered in all four
themes at the largest text size, so they must not need a network or a
device capability.

Write plain, factual English. Describe only what you ran. No marketing words.

## 10. The loop

From your copy of `platforms/ios` (set `DEVELOPER_DIR` if Xcode is not the
selected developer directory):

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer

Scripts/verify.sh --component MonarchBadge   # the fast loop, a few seconds
Scripts/lint.sh --fix Sources/MonarchUI/Components/DataDisplay/MonarchBadge   # reformat your files
Scripts/verify.sh --local                    # everything on the host, before handing over
Scripts/verify.sh --sample                   # builds the catalogue app, so your page compiles
```

`--component` takes the Swift type, the title or the id. It regenerates the
generated files, lints only your files, builds on the host and runs your
suite, your fixtures in the matrix and your compiled examples. It never
starts a simulator. `--local` lints and tests everything on the host and
skips what only the merge can decide (the API baseline). Neither compiles
`Sample/`: the catalogue page is an iOS app target, so `--sample` builds it
with `xcodebuild` for the simulator SDK (it needs XcodeGen and boots no
simulator; allow about a minute). None of these is a substitute for the full `Scripts/verify.sh`, which is run on the merged
tree.

If `Scripts/generate.py` reports a problem, the message names the file and
the rule.

## 11. Worked example: `MonarchBadge`

Plan entry: `id` `badge`, `family` `data-display`, `ios.coverage` `build`,
`ios.name` `MonarchBadge`, `dependsOn` `text`.

| File                                                                              | What is in it                                                                                                                                                                                                             |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Sources/MonarchUI/Components/DataDisplay/MonarchBadge/MonarchBadge.swift`        | The public view. Parameters in the standard order, all but the text defaulted. Reads nothing but its tokens; draws with `.monarchSurface(_:in:)`; text with `.monarchTextStyle`; icon with `MonarchIcon`; one `#Preview`. |
| `Sources/MonarchUI/Components/DataDisplay/MonarchBadge/MonarchBadgeVariant.swift` | The second public type, in its own file: `subtle`, `solid`, `outline`.                                                                                                                                                    |
| `Sources/MonarchUI/Components/DataDisplay/MonarchBadge/MonarchBadgeTokens.swift`  | Internal. Padding and spacing from `MonarchTokens.Space`; `appearance(tone:variant:)`, a pure function that maps the public variant to `MonarchToneEmphasis` and asks `MonarchTonePalette`.                               |
| `Tests/MonarchUITests/Components/DataDisplay/MonarchBadgeTests.swift`             | `MonarchBadgeFixtures` (id `badge`: every tone in every variant, and one with an icon) and `MonarchBadgeTests` (the appearance function for each variant; tones are distinct).                                            |
| `Sample/Sources/Sections/DataDisplay/MonarchBadgeSection.swift`                   | `MonarchBadgeSection: CataloguePage`.                                                                                                                                                                                     |
| `inventory/badge.json`                                                            | The documentation and one compiled example.                                                                                                                                                                               |

It has no built-in strings, so it has no strings table. For a component
with one, see `Components/Actions/MonarchButton/MonarchButtonStrings.swift`
and `Resources/en.lproj/MonarchButton.strings`. For a style, see
`Components/Forms/MonarchCheckboxToggleStyle/`. For documentation-only
entries, see `inventory/switch.json` (native) with
`Sample/Sources/Sections/Forms/SwitchSection.swift`.

## 12. Definition of done

- [ ] Only new files, at the paths in section 2. No existing file changed.
- [ ] The type name is `ios.name`; one public type per file; every public
      declaration has a documentation comment.
- [ ] A style on the standard control where one exists; a wrapper only where
      it adds value.
- [ ] No literal colour, no token colour read directly, no literal size
      where a token exists, no fixed font size.
- [ ] Leading and trailing only. Works at the largest text size. 44-point
      touch targets. Reduce Motion honoured.
- [ ] VoiceOver role, label, value and state are set; nothing depends on
      colour alone; decorative images are hidden.
- [ ] Built-in strings are in `<Name>.strings` and each has an override
      parameter.
- [ ] Fixtures cover every variant, size, tone and state.
- [ ] `<Name>Tests` covers the colour, state and accessibility logic.
- [ ] A `#Preview` with `MonarchPreviewMatrix`.
- [ ] A catalogue page.
- [ ] `inventory/<id>.json` has every field filled truthfully, and every
      example compiles and renders.
- [ ] `Scripts/verify.sh --component <Name>` passes.
- [ ] `Scripts/verify.sh --local` passes.
- [ ] `Scripts/verify.sh --sample` passes.
- [ ] Handed over: the list of new files, anything kept private that should
      be shared, and anything in the plan entry that turned out to be wrong.
