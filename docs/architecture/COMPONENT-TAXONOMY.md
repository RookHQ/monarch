# Component taxonomy (Monarch 0.4)

Every Monarch component has one **category** (what it is for) and one
**layer** (how much it composes). Both are recorded per component in
[`registry/components.json`](../../registry/components.json). The tables below
are generated by `npm run docs:generate`; do not edit them by hand.

## Categories

The 22 categories are listed in
[`registry/component-categories.json`](../../registry/component-categories.json)
and every component in
[`registry/component-demand.json`](../../registry/component-demand.json) is
filed under exactly one. A category is a filing location, not a package: one
package entry can hold components from several categories.

Categories with few or no in-scope components are those whose elements are

second or third product needs the same thing.

## Layers

Five layers, as described in
[PACKAGE-ARCHITECTURE](PACKAGE-ARCHITECTURE.md#layers). A higher
layer may compose lower ones, never the reverse.

| Layer             | What it is                                                                   | Owns business logic? | Examples in scope                                       |
| ----------------- | ---------------------------------------------------------------------------- | -------------------- | ------------------------------------------------------- |
| primitive         | Smallest building block; one element or one formatter                        | No                   | `form-field`, `search-input`, `avatar`, `relative-time` |
| component         | Self-contained, functional element with its own state and keyboard model     | No                   | `data-table`, `date-picker`, `command-palette`          |
| pattern           | Composition of components that solves one recurring interface problem        | No                   | `record-header`, `custom-domain-connect`, `filter-bar`  |
| template          | Page-level structure: regions and their responsive behaviour                 | No                   | `rook-rail`, `support-panel`, `identity-bar`            |
| product-extension | Reusable experience derived from one product's needs, on Monarch foundations | No; product keeps it | none in scope today                                     |

A component's layer is recorded in the demand data and corrected there when it
looks wrong for the target design; the package placement below decides the
build.

### Rules for layers

1. **No business logic at any layer.** Components take data and callbacks.
   Fetching, permissions, workflow transitions and validation rules stay in the
   product.
2. **A database entity is not a component.** A "customer profile" is a
   pattern made of a record header, description list, activity timeline and
   notes; it is not one card.
3. **Product extensions stay in the product** until 2+ products need them
   ([PACKAGE-ARCHITECTURE](PACKAGE-ARCHITECTURE.md)). When promoted, a
   cross-app Rook platform piece goes to `@rookcom/monarch-react/shell`; anything
   else becomes a generic component with the product noun removed.
4. **Templates own layout, not content.** They expose slots; products fill
   them.

## Naming rules

These extend the [component contract](../guides/component-contract.md).

1. **Id**: kebab-case, generic, singular noun for the interaction:
   `entity-picker`, not `member-picker` or `contact-select`. The id is the
   key in the registry.
2. **Export**: PascalCase of the id (`EntityPicker`). Parts are prefixed with
   the parent (`DialogTitle`, `TableRow`). Hooks are `useX` (`useToast`,
   `useConfirm`). Pure helpers are camelCase (`initials`, `pageWindow`).
3. **No product names in generic components.** `RookRail` is allowed only in
   `@rookcom/monarch-react/shell`, because it encodes a Rook cross-app contract
   (`rook_rail` cookie). A single product's issue card is not a Monarch component.
4. **Name the interaction, not the look.** `SegmentedControl`, not
   `PillTabs`; `ConfirmDialog`, not `RedModal`.
5. **Capabilities are props, not new components.** Async loading,
   type-to-confirm, URL-synced state and responsive card layout are recorded as
   capabilities of one component.
6. **CSS and state**: one `mn-<id>` root class, `data-*` attributes for
   state; both are public API and follow semver
   ([versioning](../governance/versioning.md)).

## Where each in-scope component sits

Package and entry point follow [PACKAGE-ARCHITECTURE](PACKAGE-ARCHITECTURE.md);
wave follows the [roadmap](../roadmap/COMPONENT-IMPLEMENTATION-ROADMAP.md);
both come from [`registry/roadmap-waves.json`](../../registry/roadmap-waves.json).
Existing exports keep their current entry point, because moving them would be
a breaking change. Wave `–` means no work is scheduled (complete today).
